# 마비노기 모바일 생활 도우미

상위 폴더의 `start.bat`으로 PySide6 화면을 실행합니다. Python·설정·데이터·문서는 모두 `workshop` 폴더 안에 있습니다. Python 3.11 이상이 필요하며, `workshop` 폴더에서 `python -m pip install -r requirements.txt`로 의존성을 설치합니다. 게임에 입장한 뒤 품목과 수량을 담고 시작합니다. 게임 조작은 CLI만 사용하며 OCR·화면 좌표 클릭은 사용하지 않습니다.

앱 아이콘은 `assets/workshop-128.png`(128×128)와 `assets/workshop.ico`에 있습니다. 창과 작업 표시줄에 ICO를 적용합니다. BAT 파일 자체의 탐색기 아이콘은 Windows 기본 아이콘이며, 필요하면 바로가기 아이콘으로 ICO를 선택할 수 있습니다.

## 작업 순서

목표 목록 아래 **가방에 있는 수량 포함** 토글로 기준을 선택합니다. 켜면 최종 보유량, 끄면 시작 시 가방 수량에 입력 수량을 더한 추가 확보량입니다. 강철괴 100개를 가진 상태에서 40개를 입력하면 켜짐은 이미 달성, 꺼짐은 최종 140개 이상 확보가 목표입니다. 생산 단위에 따라 초과할 수 있습니다.

추가 확보 모드는 첫 실행 시 최종 목표를 저장합니다. 중단·화면 복구·프로그램 재시작 후 이어하기에서도 같은 고정 목표를 쓰며 현재 보유량에 다시 더하지 않습니다. 완료 후 새로 시작할 때 새 기준을 잡습니다. 토글은 프리셋에도 저장되며 이전 프리셋은 가방 포함으로 유지합니다. 하위 재료는 두 모드 모두 기존 재고를 활용합니다.

전체 목표와 하위 재료를 함께 계산하고, 현재 재고와 등록된 가공의 산출량을 차감합니다. 재료가 준비된 가공부터 시작하며 전체 재료가 모일 때까지 기다리지 않습니다.

1. 가진 재료로 해당 시설의 대기열을 최대 7칸까지 채웁니다.
2. 다른 시설에서도 가능한 가공을 시작합니다.
3. 재료가 있는 제작은 필요한 횟수를 묶어서 요청합니다.
4. 가공 중에는 부족 재료를 채집합니다. 처음부터 재료가 없다면 우선 1회분부터 확보하여 가동합니다. 다른 시설도 가동할 수 있으면 먼저 시작합니다.
5. 시설의 현재 일감이 모두 끝나면 채집 중지를 요청하고 응답을 확인한 뒤 일괄 수령합니다. 수령한 시설에서 추가 가공이 가능하면 바로 채우고 다음 시설로 갑니다.
6. 매 행동 후 실제 재고·대기열로 계획을 다시 계산합니다. 실행할 작업이 없을 때만 가공 상태를 기다립니다.

예: 철 광석 80개, 철괴 최종 100개라면 먼저 70개로 7회 가공을 등록합니다. 남은 전체 필요량은 철 광석 260개이며 가공되는 동안 모읍니다. 생산 단위가 3개이므로 철괴는 최소 102개가 됩니다. 게임의 추가 산출과 채집 묶음에 따라 결과가 더 많을 수 있습니다.

철괴 100개와 강철괴 100개를 함께 지정하면 강철괴에 들어갈 철괴와 마지막에 남길 철괴를 합산합니다. 공통 재료의 생산 단위 올림도 합산 수요에 적용합니다. 이미 등록된 일감에 사용한 재료를 다시 채집하지 않습니다.

같은 시설의 다른 품목과 완료 미수령 일감도 슬롯을 점유합니다. 다른 시설은 동시에 가공되지만 캐릭터의 이동·채집·제작 명령은 한 번에 하나씩 실행합니다. 제작은 CLI가 응답할 때까지 다른 행동으로 전환하지 않습니다. 가공은 CLI 제약상 한 일감씩 등록하며, 등록 요청 자체를 묶을 수는 없습니다. 시설 대응을 모르는 품목은 첫 등록 후 반환되는 시설명을 확인합니다.

보관함 재료는 생산 재료 계산에만 반영합니다. 최종 목표는 가방 기준입니다. 보관함 재료가 남아 있으면 소비 작업을 마친 뒤 가방에 남길 원재료를 채집하여 중복 채집을 줄입니다.

상세 점검표: [SCHEDULING.md](SCHEDULING.md).

## 레시피와 한계

`recipes.json`에는 공개 표에서 CLI 이름·산출량과 연결된 가공 75개, 제작 401개가 들어 있습니다. 생성 시 자기 자신을 재료로 참조하는 행, `+`가 잘못 붙은 원재료, 공개표 오탈자를 검사합니다. 실행 중에도 현재 CLI의 `MissingIngredients`가 같은 수량의 자기참조·등급 오기·유사 명칭을 발견하면 그 항목을 교체합니다. `MissingIngredients`는 부족한 항목만 반환하므로 확인되지 않은 공개표 재료는 보존합니다. 모든 재료 수량이 최신 게임과 검증됐다는 뜻은 아닙니다.

표에 없는 충분한 재료의 미래 소비량은 아직 알 수 없으므로, 그 재료가 부족하다고 확인되는 시점에 계획이 보완됩니다. 구매·교환 전용 재료, 레벨·도구·전송 비용 제한은 사유를 표시합니다. 무기·방어구는 CLI 가방 수량 조회 대상이 아니므로 최종 보유량 목표로 자동 실행하지 않습니다. 기타 조회 불가 품목도 재고가 늘지 않으면 중단합니다.

전체 괄호 이름을 같은 아이템으로 합치지 않습니다. 확인된 철괴 원료 경로 두 개만 같은 철괴로 계산하고 색상·등급 품목은 구별합니다. CLI가 같은 완전한 레시피 행을 중복 반환하면 하나로 합치며, 실제로 다른 원료 경로만 설정에서 고르게 합니다. 철괴 기본 경로는 설정에서 고르며, 목표에 정확한 원료 경로를 지정하면 그 경로를 사용합니다.

## 상세 진단 로그

모든 CLI 요청·응답(원문 stdout/stderr·반환 코드·소요 시간), 재고·보관함·가공 대기열 스냅샷, 계획·레시피 후보·중복 병합·예외 traceback을 `logs/lifestyle-프로세스번호.log`에 JSON 한 줄 형식으로 계속 기록합니다. 프로그램을 동시에 여러 번 실행해도 Windows에서 로그 순환이 막히지 않도록 파일을 분리합니다. 실행마다 `run_id`가 붙어 한 번의 작업 흐름을 추적할 수 있습니다. 파일은 20MB씩 최대 5개까지 순환 보관하며, 화면에는 짧은 상태만 표시합니다. `레시피 조회 결과가 모호합니다`가 다시 발생하면 해당 시각의 `recipe.query_candidates`, `recipe.candidates_merged` 또는 `recipe.ambiguous` 이벤트와 같은 `run_id`를 확인하면 됩니다.

자료 갱신: `python build_recipes.py`, `python build_facilities.py` (게임 입장 및 `beautifulsoup4` 필요). 일반 실행에는 인터넷이 필요하지 않습니다.

## 품목 선택·프리셋

채집/가공/제작/전체 탭에서 검색하고 카드 수량을 조절해 담습니다. 시설 선택으로 목록을 좁힐 수 있습니다. 금속은 제공된 게임 화면 순서, 나머지는 시설별 CLI 반환 순서입니다. `facilities.json`에 대응 정보와 출처를 저장하며 연결되지 않은 품목은 미분류입니다.

텍스트 입력도 지원합니다: `목재 30, 실크 10`, `목재,30,실크,10`, `최상급 거미줄 1000개`. 직접 채집 가능한 품목은 채집 경로를 우선합니다.

현재 목표·날개 한도·복구 모드·기본 레시피를 프리셋 이름으로 저장합니다. 오른쪽 프리셋 버튼을 누르면 해당 설정을 적용하고 즉시 시작합니다. 실행 중에는 다른 프리셋을 시작하지 않습니다. 설정과 프리셋은 `settings.json`에 저장됩니다.

입력값은 변경 후 0.3초 뒤 자동 저장하고 정상 종료할 때도 마지막 값을 저장합니다. 시작 버튼을 누르지 않아도 목표 목록, 카드별 미확정 수량, 작성 중인 텍스트·프리셋 이름, 날개 한도, 가방 포함 체크, 복구 방식, 검색어, 선택 탭, 탭별 시설, 기본 레시피 선택과 CLI 경로를 복원합니다. 기본 레시피 드롭다운 변경도 즉시 적용·저장됩니다. 게임 품목을 늦게 불러와도 시설과 레시피 선택은 목록을 받은 뒤 복원합니다. 재실행 시 생산을 자동 시작하지 않으며, 작업 중단 기록과 추가 확보의 고정 목표는 화면 입력과 별도로 유지합니다.

카드의 이미지 연결은 로컬 PNG/WebP/JPG 경로를 사용합니다. 실제 게임 패키지에서 아이콘을 자동 추출하는 기능은 없습니다. 이미지가 없으면 이름 약자를 표시합니다.

## 채집·중지·이어하기

현재 가방 무게가 최대 무게의 90% 이상이면 채집을 시작하지 않으며, 채집 중 도달해도 중지합니다. 이 상태에서도 가공 등록·제작·완성품 수령은 계속 진행합니다. 가능한 작업이 없으면 15초마다 무게와 재료를 재확인하며 기다립니다. 90% 아래로 내려가면 채집도 재개합니다. 자동 창고 보관·판매는 하지 않으므로 소비할 재료가 없으면 사용자가 가방을 비울 때까지 대기할 수 있습니다.

채집 중 15초마다 재고·가공 가능 여부·대기열을 재확인합니다. 놀고 있는 시설이나 대기열 잔여 시간이 10분 이하인 시설은 준비되는 즉시 보충하고, 대기열이 넉넉하면 최대 3회분의 보충 재료를 모아 방문합니다. 오래 걸리는 대기열에서 완료품이 슬롯을 막으면 일부 완료품도 수령하여 보충합니다. 짧은 대기열은 일괄 완료를 기다려 왕복을 줄입니다.

시설이 일부 가동 중이어도 빈 슬롯이 있으면 다음 1회분을 막는 재료부터 확보합니다. 중간 가공품이 부족한 상위 레시피보다 원재료만 채집하면 등록할 수 있는 레시피를 우선합니다. 예를 들어 진액 319개·최상급 통나무 7개라면 전체 진액 목표를 채우기 전에 통나무 13개를 먼저 채집합니다. 채집 중 점검에서도 이 우선순위를 다시 계산하여 대상 변경이 필요하면 중지 후 전환합니다.

나무 진액은 부드러운 통나무가 채집 가능하고 도구가 있을 때 해당 경로로 채집하며, 종료 수량은 진액 재고로 판단합니다. 통나무 등 부산물은 다음 계획에서 실제 재고로 반영합니다. 통나무 채집이 두 번 완료되는 동안 진액이 늘지 않으면 직접 진액 채집으로 전환합니다. 현재 CLI 경로가 실제로 뾰족나무를 선택하는지는 실게임 검증이 필요합니다.

- 채집 중 0.5초 간격으로 가방 수량을 확인하고 목표에 도달하면 중지를 요청합니다. 관련 시설 완료도 주기적으로 확인합니다. 획득 묶음과 응답 지연으로 초과 획득할 수 있습니다.
- 한 채집 요청은 최대 100개이며, 필요하면 다시 요청합니다. 낚시는 시작 응답 후에도 수량을 감시하고 목표 도달·시설 완료·사용자 중지 시 종료를 요청합니다.
- 중지 명령이 이동/채집 완료와 겹친 경우 실제 응답을 확인합니다. 이전 작업 응답이 끝나기 전에 다음 게임 행동을 보내지 않습니다.
- 실행 요청당 날개 5개로 한도를 계산합니다. 실패 요청도 포함하므로 실제 지출보다 보수적입니다. 제작 최대 횟수는 CLI의 `invalid_count / maxCount` 응답을 반영하며 해당 요청도 한도에 포함합니다.
- 화면 차단 시 수동 이어하기 또는 ESC 자동 복구를 선택할 수 있습니다. 자동 ESC는 `unknown_modal`이고 전면 창이 게임일 때 한 실행에서 최대 2회만 시도합니다.
- CLI가 일시적으로 `not_in_game`을 반환하면 15초마다 인벤토리 조회로 접속을 확인하며, 중지 요청 전까지 횟수 제한 없이 기다립니다. 복구되면 재고·가공 일감을 다시 읽어 계획을 세웁니다. 작업 명령이 시간 초과되어 진행 여부가 불명확하면 이전 동작의 중지를 확인한 후 재계획합니다.
- 이어하기는 실제 재고·등록 일감을 다시 읽고 진행합니다. 동일한 미완료 목표의 실행 요청 횟수도 유지합니다.
- 목표와 요청 횟수를 설정 파일에 저장합니다. 강제 종료 직전 UI 저장이 아직 반영되지 않은 요청은 누락될 수 있습니다.
- 사용자가 중지해도 이미 등록된 가공은 게임에서 계속됩니다. 시설 수령 시 사용자가 별도로 등록한 완료 일감도 함께 수령될 수 있습니다.

## 검증

`python -m unittest discover -v`로 테스트합니다. 실제 게임 재화를 쓰지 않는 모의 CLI에서 재고 소비·가공 큐·시설별 시간·채집 중지·재개·최종 수량을 검증합니다. 실제 CLI 읽기 전용 조회와 모의 실행 통과는 실제 게임에서의 생산 완주와 구분합니다.
